### 使用者

Test Task可以根據測試項目的執行狀況計算出工作進度
Plan Task如果也要有工作進度可以查詢, 有甚麼可計算的根據?(先評估, 不做任何改動)


### 助理結論（歷史）

可以。**Plan Task 最適合以「工作項目或里程碑的完成情況」計算進度**，前提是先定義可確認完成的工作內容。

核對本機後，Plan Task 目前有 Status、Assignee、計畫／實際日期與 History，但尚無工作清單、里程碑或完成量。因此，現有資料只能表示工作狀態與時間經過，還不足以算出可靠的完成百分比。

可考慮以下依據：

| 計算依據 | 計算方式 | 適用情況與限制 |
|---|---|---|
| 工作清單 | 已完成項目數 ÷ 總項目數 | 最簡單，適合各項工作量接近的任務 |
| 加權里程碑 | 已完成里程碑的權重加總 | 適合文件、設計、開發等各階段工作量不同的任務 |
| 交付數量 | 已完成數量 ÷ 目標數量 | 適合整理 20 份資料、完成 10 台設備設定等可量化工作 |
| 人工填報百分比 | Assignee 填寫 0～100% 與說明 | 彈性高，但仰賴個人判斷，需保留更新紀錄 |
| 計畫日期 | 已經過工作天 ÷ 計畫工作天 | 可表示「預期進度」，無法證明實際工作已完成 |

我較建議 **工作清單搭配可選權重**。一般任務預設每項等權重，需要時才調整。例如「完成測試計畫文件」可以拆成：

| 工作項目 | 權重 | 完成情況 |
|---|---:|---|
| 確認測試範圍 | 20% | 已完成 |
| 完成測試項目與 Criteria | 40% | 已完成 |
| 完成審查與修訂 | 30% | 進行中 |
| 發布文件 | 10% | 未開始 |

此時進度為 **60%**。每一項需要有明確完成條件，例如「審查意見已處理並確認」，勾選完成後才計入權重。這樣查詢進度時，也能知道剩下哪些工作。

狀態與進度的關係建議採以下規則：

- **On-Going** 可以是不同百分比，不能固定換算成 50%。
- **Pending** 保留暫停前的進度，並顯示暫停原因。
- **Cancel** 保留取消時的進度，避免被計為完成。
- **Complete** 應與必要工作項目全部完成一致。
- 尚未建立工作項目時顯示「未設定」，避免將未知進度當成 0%。

若只想用最少操作先建立進度查詢，人工填報百分比也可行；若希望進度能追溯依據、方便主管確認剩餘工作，工作清單會比較合適。

本次僅評估，未修改程式或資料。

### 使用者

假設目前建立了一個Plan, 也透過test task儲存了測試結果, 但是後來Plan裡面的test case有變動, 對於已經執行過的test task會有甚麼影響


### 助理結論（歷史）

依目前實作，**Test Task 引用的是 Plan 目前的測項，不是執行當時的獨立快照**。因此即使已執行完成，Plan 後續變更仍會影響它。

| Plan 的變動 | 對已執行 Test Task 的影響 |
|---|---|
| 新增 Test Case | 不會自動加入既有 Task；需在 Scope 勾選，新加入項目為未執行 |
| 修改測項 `.py`、Parameters／Preset | 保留既有結果與 Log，將受影響項目標示為「需重測」；再次執行使用修改後的內容 |
| 移動測項或調整資料夾結構 | 測項 ID 不變時，結果保留，顯示位置跟著目前 Plan 結構改變 |
| 刪除 Test Case | **所有相關 Task 中該測項的 Scope、結果與 Log 都會被刪除**，Task 本身保留 |
| 刪除包含測項的資料夾 | 同上，連帶移除資料夾內測項的相關結果 |
| 刪除整個 Plan | **連帶刪除所屬 Test Task 與結果資料** |

另需注意：**重新執行某個測項時，會先清除該項原有結果與 Log，再記錄本次結果**，目前沒有保留每次執行版本的機制。

例如 Task 已完成 A、B、C：修改 B 會保留 B 的舊結果並提示重測；刪除 C 則會讓 C 及其結果從 Task 消失。因此，目前的 Task 無法作為「完成後固定不變的測試紀錄」。

若你的需求是保留當時的測試內容與證據，後續應調整為：**Plan 可持續修改，但已執行 Task 保存當時的測項版本，Plan 的修改或刪除不得連帶移除其結果。**
